The GitHub App must be verified as the App independently of the inspecting CLI identity. An organization owner can confirm the selected repository in installation settings, or an authorized operator can verify repository installation with the App's JWT without disclosing that JWT. Use the real App's user authorization for the linked user. Installation permission alone does not establish that user's access. ### Smallest operator and UI sequence

1. **Select one test repository/workflow already installed and one authorized user.** The owners of the Entra registrations and GitHub App confirm account/repository/workflow numeric IDs, exact authorized HTTPS callback, enterprise/SSO grant and effective user rights. Ingestion owners confirm admission source, custody identity and approved secret references out of band. Never hand credentials to the SPA or put them in a runbook.
2. **Wire the existing ports after approval of the callback binding.** Supply the actual `ingestion.api.security` issuer/JWK URI, tenant, audience, token version, self/internal scopes and caller allowlists, plus `ingestion.api.limits`. Use retained PostgreSQL connection metadata and approved custody composition. Wire Pipeline's OBO adapter against Ingestion's internal verification contracts before attempting real registration. Provider/custody failure, expired attempts, rejected audiences, replay, revoked links and denied installations must fail closed.
3. **Reuse Pipelines and Add Monitored Workflow.** Once a real session is available, read status in Pipelines. Show loading, unlinked, linked locally, denied and unavailable distinctly. Load verified repositories and workflows only with a valid session; bind the workflow list to the current selected repository and discard stale responses after selection or identity changes. Attach **Connect/Reconnect** only to the approved start flow. Offer **Disconnect** only for the current link and use its ETag; on conflict reload status. Clear the identity and catalog on denial, disconnect or authority failure. Registration still sends selected IDs and operational configuration to Pipeline. It sends no access flags. Verify an actual provider discovery, administrator registration and persisted reload, with revoked access and provider outage checks before advisor use.
4. **Today:** the UI labels GitHub linking unavailable and identifies the isolated catalog as synthetic in the pilot. There is no connected identity or enabled linking control. Switching to the pilot is explicit. Ingestion's test verification covers HTTP, delegated identity, PostgreSQL metadata, private OAuth transport, custody and provider reads with doubles. It does not activate OAuth with the installed App. Follow the [Ingestion deployment contract](https://github.com/pipesor-org/pipesor-ingestion-normalization-service/blob/main/docs/deployment-contract.md) for PD-027/034/035 approval and runtime handoff.

The minimum academic implementation is a versioned manifest and a sanitized offline evidence export from existing owner verification runners. No dashboard database access or analytics service is needed. Operational aggregates can follow the existing authorized read surfaces after cohort and projection decisions. The ten-scenario, 1,000-log and 80% thresholds remain unevaluated.
